# Phase 34: client-side WebGPU inference

Phase 34 provides an inference-only browser runtime for the frozen Leda Demo v0 model. It is a
static-hosting component: model execution happens in a Web Worker through WebGPU, and scientific
text is not sent to an inference service. This is the numerical runtime and diagnostic harness;
the user-facing website belongs to Phase 35.

## Implementation boundary

The runtime uses a TypeScript controller and purpose-built WGSL compute shaders. This boundary was
chosen instead of compiling native Spar through Emscripten because the browser needs only the
frozen inference graph, not C++ modules, autograd, training, datasets, or checkpoint writing. It
also avoids depending on ONNX, Transformers.js, TensorFlow.js, WebLLM, or another model runtime.

Native Spar remains free of JavaScript and browser dependencies. Leda owns both the browser runtime
and the offline conversion tools because the graph and frozen model configuration are Leda-specific.

## Execution model

The worker accepts `INIT`, `COMPLETE`, `NEXT_TOKEN`, `CANCEL`, and `STATUS` requests. Request IDs
isolate concurrent callers and suppress stale completion events. Initialization reports capability
checking, download, verification, GPU upload, and ready states. Completion uses fixed-capacity,
device-resident K/V caches with unexpanded GQA geometry `[2, 512, 64]` for each of the 12 layers.

The runtime implements only embedding lookup, RMSNorm, tiled linear projection, Q/K normalization,
RoPE, grouped-query attention, softmax, residual addition, SwiGLU, the tied output projection, and
sampling. Prompt plus completion is strictly limited to 512 tokens. Generated bytes are passed
through a streaming UTF-8 decoder because a byte-BPE token need not be a complete character.

## Browser artifact

`leda_export_web` converts the frozen `SPARCKPT v1` checkpoint into deterministic `LEDAWEB v1`.
The little-endian file has a fixed header, aligned tensor records, and aligned Float32 parameter
payloads. It contains only model metadata and 134 Parameters (40,385,024 Float32 values); optimizer,
gradient, RNG, iterator, and training-progress state are excluded.

Frozen Float32 artifact:

- bytes: `161,550,016`
- SHA-256: `2afdc9c772af3f6f6cceb71506e98e528cded43143c927304875614f04e7adac`
- source checkpoint SHA-256: `a94e2a15977c811b2bc8a7bb1e87be45510e3d350f08b21ef599644ba3fd1bed`
- tokenizer SHA-256: `04345687338f13b1b8e8d219dae265094a708bf8d1b409541748cb2d89424970`

The runtime checks both downloaded artifact hashes and the checkpoint identity recorded inside the
model artifact. Immutable assets are cached in Cache Storage under a format-versioned key. Invalid
or stale entries are discarded. `SPARCKPT v1` and `SPARTOKN v1` are unchanged.

## Numerical validation

The committed `LEDAREF v1` fixture contains synthetic token inputs and native Float32 logits; it
contains no checkpoint, corpus, or held-out test text. Chrome Dev on an Apple M3 matched native
tokenizer encode/decode for ASCII, Unicode, Greek, chemistry, scientific notation, and embedded raw
bytes. All 41 tested prefill/decode positions selected the same greedy token as native Spar.

| Prefill + decode | Maximum absolute logit error | Maximum relative logit error | Greedy agreement |
|---:|---:|---:|---:|
| 1 + 3 | 2.26498e-5 | 4.44286e-4 | 4/4 |
| 17 + 3 | 1.28746e-5 | 1.30217e-2 | 4/4 |
| 32 + 3 | 2.67029e-5 | 3.41481e-2 | 4/4 |
| 127 + 3 | 1.85966e-5 | 8.55323e-3 | 4/4 |
| 128 + 3 | 2.33650e-5 | 9.96397e-3 | 4/4 |
| 256 + 3 | 2.09808e-5 | 5.98806e-4 | 4/4 |
| 400 + 3 | 1.81198e-5 | 1.88373e-2 | 4/4 |
| 500 + 12 | 2.57492e-5 | 1.86383e-2 | 13/13 |

Relative error uses `max(abs(reference), 1e-6)` as its denominator, so the largest relative values
occur at logits close to zero. The worst absolute error is `2.67029e-5`.

## Measured performance

Warm Chrome Dev measurements on Apple M3/Metal are shown below. Download timing was over localhost
and is not representative of first-load internet latency. Checkpoint loading is excluded.

| Prompt tokens | Prefill | TTFT | Cached decode | Total 32-token latency |
|---:|---:|---:|---:|---:|
| 32 | 22.6 ms | 25.0 ms | 91.66 tok/s | 363.2 ms |
| 128 | 36.0 ms | 38.1 ms | 90.56 tok/s | 380.4 ms |
| 256 | 70.4 ms | 73.5 ms | 88.37 tok/s | 424.3 ms |
| 400 | 111.7 ms | 115.0 ms | 81.13 tok/s | 497.1 ms |

GPU initialization took approximately 61 ms after the 161,550,016-byte model was available. The
runtime accounts for approximately 181,268,488 bytes of WebGPU buffers. The tested adapter exposed
`maxBufferSize=268435456`, `maxStorageBufferBindingSize=134217728`, and 256 compute invocations per
workgroup. No single 154 MiB binding is required.

## Privacy and offline behavior

An empty-cache integration run observed one model request and one tokenizer request during first
initialization. A second worker reused both cached immutable assets. Model completion then issued
zero network requests. Cancellation after the first generated token produced no stale events, and
a superseded request produced no token events. During a 32-token completion, a 10 ms main-thread
timer continued to fire, confirming that model execution remains off the UI thread.

## Browser support and deployment choice

Chrome Dev on Apple M3/Metal is the validated Phase-34 target. The adapter did not expose
`shader-f16`, so Phase 34 deliberately retains the correctness-first Float32 path. Safari and
Firefox were not validated in this phase and must not be advertised as supported until tested.
Unsupported browsers receive a structured WebGPU capability error; there is no CPU/WASM fallback.

Phase 35 should ship the Float32 `LEDAWEB v1` artifact identified above. Its first-load size is the
main known UX cost. F16 and weight-only INT8 remain measured future investigations rather than
unvalidated deployment defaults.
